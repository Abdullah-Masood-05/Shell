Win+X menu (experimental)


The Win+X menu is the menu that opens with Win+X or a right-click on the Start button. Shell draws it like any other menu, and a configuration can add items to it or replace Windows' own items. Support for it is experimental: test it before relying on it, and see Troubleshooting if the menu is not recognised.

Targeting the menu

Use type='winx' (or the older name type='start') to show an item only in the Win+X menu, and window.is_winx (or window.is_start) in expressions. The Win+X menu is not a taskbar menu: type='taskbar' does not match it, although window.is_taskbar is true there, as it is for every menu opened from the taskbar.

item(type='winx' title='&Task Manager' image=image.mdl(\uE9D9) cmd='taskmgr.exe')
item(where=window.is_winx title='Services' cmd='services.msc')

On Windows 11, configurations that used the workaround type='taskbar' where=window.parent.name == null should use type='winx' instead.

Settings
settings
{
	winx
	{
		// Show only the configured items; Windows' own items are left out.
		replace = true

		// Log how every taskbar and Win+X popup was recognised to shell.log.
		debug = true
	}
	// or, short for winx.replace = true
	winx = true
}
replace
Off by default, which adds the configured items to Windows' own. When on, Windows' items are not read at all (this.count is 0), so no modify rule can show, move or rename one. Explorer numbers its Win+X commands by its own list of entries, and editing those entries used to crash it; with replace the menu can only return a command Explorer put in it or none, and Shell runs its own items itself.
debug
Off by default. Writes one line per taskbar or Win+X popup to shell.log; see Troubleshooting.
Access keys

An & before a letter in a title makes that letter the item's access key, as in Windows' own menu: press Win+X, then the letter. Write && for a literal ampersand. In the Win+X menu the keys are always underlined and work without setting theme.item.prefix. When several items share a letter, pressing it moves between them and Enter runs the highlighted one.

The power-user menu (imports/winx.nss)

Shell ships imports/winx.nss, which is not imported by default. Remove the // from this line at the end of shell.nss to use it (or turn on "Win+X menu" under Context Menus in the Nilesoft Shell Pro app):

// import 'imports/winx.nss'

It turns on winx.replace and shows Terminal, Terminal (Admin), Device Manager, Disk Management, Event Viewer, Services, Task Manager, Settings, Network, Power Options, Run and a Shut down or sign out submenu (Lock, Sign out, Restart, Shut down). Sign out, Restart and Shut down ask first. Each item has an icon and an access key. The shipped Terminal and Go To menus (terminal.nss, goto.nss) still show in the Win+X menu, as they do for every menu opened from the taskbar; add && !window.is_winx to their where to leave them out.

Troubleshooting

The first Win+X menu after Explorer starts is noted in shell.log (next to shell.dll, or %LOCALAPPDATA%\Nilesoft\Shell\shell.log when that folder is not writable). With settings.winx.debug = true every taskbar or Win+X popup is logged:

[info] Win+X menu: recognised by caller module (window 'Shell_TrayWnd'; callers twinui.pcshell.dll < ...; 9 of 41 stack frame(s) attributed).
[info] Win+X menu: replace is on; 18 Windows item(s) are left out.
[info] Win+X menu: 0 Windows item(s) (this.count), 15 configured top-level item(s), 0 system and 15 new item(s) to show, replace on.
[info] Win+X menu: access key 'K', 1 match(es).
[info] Win+X check: a taskbar menu, not the Win+X menu (none; window 'Shell_TrayWnd'; callers explorer.exe; 3 of 37 stack frame(s) attributed).

Windows 10 owns the menu by a LauncherTipWnd window, which is enough to recognise it ("owner class"). Windows 11 owns it by the taskbar itself, so Shell checks which code opened it: Explorer's twinui.pcshell.dll ("caller module"). If a taskbar tool sits between them, the line shows its name among the callers. Please include these lines when reporting a problem.
